# Catalog Quality & Operations Analytics

SQL analysis of catalog quality, recurring failures and historical issue backlog, with reproducible synthetic data and a Power BI model specification.

**Status:** runnable SQL foundation and validated synthetic dataset. Power BI build instructions and DAX are provided; no completed or tested `.pbix` report is included. PostgreSQL scripts are provided but have not been executed against a PostgreSQL server. The local database and all nine analysis queries were executed using SQLite.

## Business question

Which catalog problems should an operations team fix first, and is its backlog improving?

The scenario contains 10,000 listings in four marketplaces, six months of checks (May–October 2026), and issue opening/closure dates. All data is fictional. Patterns are intentionally generated, not evidence of real business impact. No Amazon data or internal systems are used.

## Start here on Windows

1. Clone this repository or download and extract its ZIP. Open a terminal in the project folder.
2. Open the extracted `catalog-quality-analytics` folder. Start with `docs/START_HERE.md`.
3. Open a terminal in this folder. With Python installed, run:

```powershell
py scripts/build.py
py scripts/query.py sql/analysis/01_monthly_trend.sql
py scripts/test_boundaries.py
```

No pip packages, accounts or database server are needed for these commands. If `py` is unavailable but Python is on your PATH, use `python` instead. Run `py scripts/build.py` first after cloning to generate the local database and CSV inputs. Selected result exports are included for quick review.

```powershell
py scripts/build.py
```

Build generates or overwrites this project's generated database, data exports, analysis results and SQL load file. It leaves the editable SQL queries and documentation intact. Python 3.10+ is required.

## PostgreSQL path

Use a new, empty database dedicated to this exercise. Run these in order in pgAdmin Query Tool, or through `psql`:

```text
psql -d catalog_quality -v ON_ERROR_STOP=1 -f sql/01_schema.sql
psql -d catalog_quality -v ON_ERROR_STOP=1 -f sql/03_load_data.sql
psql -d catalog_quality -v ON_ERROR_STOP=1 -f sql/02_views.sql
psql -d catalog_quality -v ON_ERROR_STOP=1 -f sql/analysis/01_monthly_trend.sql
```

These commands assume an installed PostgreSQL client, an existing database and your locally configured connection/authentication. They do not create a server or database. Dates are ISO-formatted TEXT for portability; production PostgreSQL should use DATE columns and stricter ingestion checks. Do not rerun the schema/load into an already populated database. Validate PostgreSQL outputs against the included CSVs before describing the project as PostgreSQL-tested.

## Evidence and limitations

`results/validation.json` records counts and executed checks. Four adversarial fixture tests cover join fan-out, closure on month-end, a zero-backlog month, and invalid closure order. Independent Python calculations match SQL rates and historical backlogs for every month.

Each listing is checked exactly once per month. Checks with multiple issue types are counted once in the affected-check rate. A repeat failure is not labelled a reopened issue. The generator does not model a full real-world ticket lifecycle, partial inspection coverage, late-arriving corrections, delisted products or financial impact. Current listing attributes and historical check events are separate synthetic examples.

Developed with AI assistance. Synthetic results are not claims of production deployment or commercial impact. The included exercises support understanding and extending the implementation.
